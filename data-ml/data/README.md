# data/

Synthetic datasets generated by `../generate_data.py` (fixed seed `42`,
fully reproducible — regenerating from scratch produces byte-identical
files, verified during packaging).

## `operations.csv`

423 rows · 15 operators (`OP-01`–`OP-15`) · 20–35 sessions each.

```
timestamp, machine_id, operator_id, engine_hours, fuel_used_l, load_cycles,
idling_time_min, seatbelt_status, distance_to_nearest_object_m,
safety_alert_triggered, training_completed_recent
```

`training_completed_recent` (`Yes`/`No`) is an addition to the original
locked `CONTRACTS.md` schema — see `../CONTRACTS_PATCH.md`. It feeds the
training-status component of the Operator Performance Score.

`safety_alert_triggered` is computed from the same rule the NestJS rule
engine uses (seatbelt unfastened OR proximity < 3m OR idling > 45min), so
the label is consistent with the backend by construction.

## `tasks.csv`

248 rows · 15 operators · 10–20 tasks each.

```
task_id, operator_id, timestamp, task_type, weather, operator_skill,
machine_age_yrs, estimated_time_min, actual_time_min
```

`operator_id` and `timestamp` are additions to the original locked schema
(see `../CONTRACTS_PATCH.md`) — required so the Operator Performance Score
and cross-feature synthesis can compute per-operator task-overrun history.
`actual_time_min` is the regression target for the task-time model; it is
never used as a model input.

## Regenerating

```bash
cd data-ml
python3 generate_data.py   # writes data/operations.csv, data/tasks.csv
python3 validate.py        # checks schema, ranges, null values, consistency
```

Do not hand-edit these files — regenerate via `generate_data.py` (seed 42)
if a change is needed, and re-run `validate.py` and `train_model.py`
afterward so the model and outputs stay in sync with the data.
